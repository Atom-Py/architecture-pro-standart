# Задание 2. Требования по группам FURPS+

Требования собраны по двум направлениям цифровизации: подача заявки на депозит (сайт и интернет-банк, этап MVP) и подача заявки на кредит (сайт и интернет-банк). Учтены ограничения текущего IT-ландшафта из первого задания.

Пометки в колонке «Комментарий»:

- **АЗТ** - архитектурно значимое требование, то есть такое, которое напрямую определяет выбор архитектуры и не может быть удовлетворено «настройкой» существующих систем;
- **Добавлено** - требование, которого не было в исходных материалах, приведено обоснование.

| Код | Требования | Комментарий |
|-----|------------|-------------|
| **F** | **Функциональные (Functionality)** | |
| F1 | Сайт показывает неавторизованному посетителю список депозитных продуктов с актуальными ставками | АЗТ. Сегодня ставки существуют только в файле Excel, поэтому нужен источник данных о ставках, доступный публичному каналу. Витрина сайта при этом не должна обращаться к АБС |
| F2 | Посетитель сайта подаёт заявку на депозит, указав Ф. И. О. и номер телефона | Клиент ещё не идентифицирован, поэтому набор данных минимальный |
| F3 | Заявка с сайта передаётся в систему кол-центра и попадает оператору для обратного звонка | АЗТ. Требуется новая интеграция между публичным сайтом и системой кол-центра, асинхронная по характеру |
| F4 | Оператор кол-центра работает с заявкой в своей системе и может предложить клиенту особые условия по депозиту | Особые условия означают ставку, отличную от базовой, значит оператору нужен доступ к ставкам |
| F5 | По итогам звонка клиент получает информацию о необходимости прийти в отделение для идентификации | Банк не может принять нового клиента без личной проверки документов |
| F6 | Интернет-банк показывает клиенту список депозитов с актуальными ставками и персональные ставки, рассчитанные лично для него | АЗТ. Персонализация требует данных о клиенте и его остатках, при этом нагружать АБС онлайн-запросами нельзя |
| F7 | Клиент подаёт заявку на открытие депозита в интернет-банке, указав счёт списания и сумму | |
| F8 | Подача заявки в интернет-банке подтверждается одноразовым СМС-кодом | АЗТ. Работа с СМС реализована в ядре платформы интернет-банка, дорабатывать ядро силами подрядчика нежелательно, поэтому отправку и проверку кода нужно вынести за пределы ядра |
| F9 | Ставки по депозитам ведутся в информационной системе: базовые ставки, сетки по срокам и суммам, индивидуальные ставки | АЗТ. Ставки становятся источником данных для всех каналов, сейчас их нет ни в одной системе кроме XLS. Наиболее вероятное место реализации - АБС |
| F10 | Со ставками работают сотрудники бэк-офиса депозитов и бэк-офиса кредитов, права доступа разграничены | АЗТ. По требованиям безопасности сотрудники депозитов и кредитов не должны видеть данные друг друга, при этом ставку рассчитывают оба подразделения |
| F11 | Согласование индивидуальной ставки по заявке выполняется внутри системы, а не перепиской по электронной почте | Сейчас цикл согласования занимает до часа и держит клиента в отделении |
| F12 | Менеджер бэк-офиса обрабатывает заявку на депозит и подтверждает её условия в АБС | На этапе MVP процесс обработки остаётся ручным и выполняется по существующему регламенту |
| F13 | Клиент получает СМС после подтверждения размера ставки и после открытия депозита | |
| F14 | Клиент видит статус своей заявки в интернет-банке | Добавлено. Без статуса клиент после отправки заявки не понимает, что происходит, и идёт в кол-центр, который в MVP и так под нагрузкой |
| F15 | Депозит открывается в АБС, договор и документы учитываются там же | Учёт операций и договоров остаётся в АБС, это её зона ответственности |
| F16 | Сайт показывает посетителю кредитные предложения с условиями | Полная информация об условиях кредита хранится в Кредитном конвейере, значит условия нужно доставлять в публичный канал |
| F17 | Посетитель сайта подаёт заявку на кредит, указав Ф. И. О. и телефон, паспортные данные заполняются по желанию | |
| F18 | Если паспортные данные заполнены, клиент получает предварительное решение по кредиту сразу на сайте | АЗТ. Требуется синхронный вызов системы скоринга из публичного канала, которого сегодня нет |
| F19 | Скоринг нового клиента выполняется только по общим данным бюро кредитных историй | Клиент новый, внутренних данных о нём в банке нет |
| F20 | После подачи заявки с сайта клиент получает СМС о необходимости прийти в отделение для идентификации и получения кредита | |
| F21 | Менеджер отделения при подаче заявки через АБС находит ранее поданную клиентом онлайн-заявку и продолжает работу с ней | АЗТ. Нужен сквозной идентификатор клиента и заявки между каналами, иначе на одного клиента заводятся две заявки и два скоринга |
| F22 | Для полностью нового клиента менеджер отделения создаёт новую заявку | |
| F23 | Интернет-банк показывает клиенту предодобренное кредитное предложение с рассчитанной суммой | АЗТ. Предложение формируется по результату ранее выполненного скоринга, значит результаты скоринга нужно где-то сохранять |
| F24 | Клиент подаёт кредитную заявку в интернет-банке, указывает счёт зачисления средств, подтверждает подачу СМС-кодом | |
| F25 | После подачи заявки по предодобренному предложению скоринг выполняется повторно по упрощённой процедуре, если ситуация изменилась | Упрощённая процедура нужна, чтобы такие заявки обрабатывались быстрее обычных |
| F26 | Клиент получает СМС об изменении статуса кредитной заявки | |
| F27 | Повторная отправка одной и той же заявки не создаёт дубликат | Добавлено. Клиент нажимает кнопку дважды, сеть повторяет запрос. Без защиты от дублей у клиента появятся два депозита или две кредитные заявки, а бэк-офис получит двойную работу |
| F28 | Ставка фиксируется в момент подачи заявки и не меняется при последующем пересчёте базовых ставок | Добавлено. Ставки обновляются ежедневно, а заявка обрабатывается вручную и может пролежать до следующего дня. Клиент должен получить ту ставку, которую видел |
| F29 | По каждой заявке ведётся журнал действий: кто, когда и какое изменение внёс | Добавлено. Требуется для банковского аудита и разбора спорных ситуаций с клиентом |
| **U** | **Удобство использования (Usability)** | |
| U1 | Интерфейсы новых разделов соответствуют принятой в компании системе дизайна: привычные цвета, типографика, брендированные элементы | Прямое требование бизнеса |
| U2 | Работа с заявкой воспринимается как мгновенная, интерфейс не блокируется на время обращений к другим системам | Требование бизнеса о максимально быстром отклике. Численные значения вынесены в группу Performance |
| U3 | Форма заявки на сайте требует минимума данных, паспортные данные запрашиваются как необязательные с пояснением, что они дают мгновенное решение | Мотивирует клиента заполнить больше данных, но не отсекает тех, кто не готов |
| U4 | Клиенту явно сообщается следующий шаг: ждать звонка оператора, прийти в отделение для идентификации, ожидать решения по заявке | Добавлено. Процессы обрываются офлайн-шагом, и без явной подсказки клиент считает, что заявка потерялась |
| U5 | Интерфейсы рассчитаны на клиентов старшего возраста: крупный шрифт, простые формулировки, минимум шагов | Добавлено. Основная категория клиентов банка - люди старшего возраста, именно они первыми пойдут в новые каналы после маркетинговой кампании |
| U6 | Сайт и интернет-банк ведут себя одинаково в одинаковых сценариях | Добавлено. Один и тот же продукт оформляется в двух каналах, расхождение в поведении порождает обращения в кол-центр |
| **R** | **Надёжность (Reliability)** | |
| R1 | Доступность сервисов подачи заявок 99,9%, режим работы 24/7 | АЗТ. Прямое требование бизнеса, текущей архитектурой интернет-банка не выполняется |
| R2 | Интернет-банк сохраняет работоспособность при отказе ЦОД и выдерживает требуемую нагрузку на резервной площадке | АЗТ. Сейчас всё работает в одном ЦОД на одной группе серверов, резервный ЦОД есть, но переключение нагрузку не держит |
| R3 | Новые сервисы разворачиваются в обоих ЦОД и обслуживают запросы одновременно | АЗТ. Иначе резервный ЦОД остаётся холодным и требование R1 не выполняется |
| R4 | Недоступность АБС не блокирует приём заявок в digital-каналах: заявка принимается, сохраняется и обрабатывается позже | АЗТ. Прямая синхронная зависимость от АБС переносит её проблемы на клиентские каналы, а БД АБС уже перегружена |
| R5 | Недоступность системы скоринга или бюро кредитных историй не приводит к отказу в приёме кредитной заявки, клиент получает отложенное решение | Добавлено. Бюро кредитных историй - внешняя система, её доступность банк не контролирует |
| R6 | Передача заявок и событий между системами выполняется без потерь, с повторными попытками доставки | АЗТ. Заявка - это деньги клиента и обязательство банка, потеря недопустима, а цепочка обработки асинхронная |
| R7 | Данные по ставкам и заявкам резервируются, предусмотрено восстановление | Добавлено. Ставки становятся источником данных для всех каналов, их потеря останавливает продажи во всех каналах |
| R8 | Для новых сервисов зафиксированы целевые значения RPO и RTO | Добавлено. Без них требование доступности 99,9% нечем проверить при приёмке |
| **P** | **Производительность (Performance)** | |
| P1 | Отклик пользовательских операций в интернет-банке и на сайте измеряется миллисекундами | Прямое требование бизнеса |
| P2 | Списки продуктов и справочные данные отдаются быстрее одной секунды | АЗТ. Сейчас при проведении платежей справочники грузятся дольше секунды. Витрина данных в канале вместо обращения к АБС |
| P3 | Онлайн-подача заявок не увеличивает нагрузку на базу данных АБС | АЗТ. Команда АБС предупреждает, что БД перегружена, а онлайн-поток заявок ставит под угрозу работоспособность банка |
| P4 | Новые сервисы масштабируются горизонтально, запросы равномерно распределяются между серверами, экземплярами приложений и ЦОД | АЗТ. Прямое требование, при этом АБС масштабируется только вертикально, значит нагрузка должна приниматься вне её |
| P5 | Предварительное решение по кредиту на сайте выдаётся в течение единиц секунд | Клиент ждёт ответа в браузере, иначе сценарий мгновенного решения теряет смысл |
| P6 | Заявка по предодобренному предложению доступна сотруднику для обработки в течение того же рабочего дня | АЗТ. Существующий обмен между АБС и Кредитным конвейером идёт раз в сутки и ускорить его невозможно, значит нужен отдельный канал доставки заявок |
| P7 | Новые процессы не создают дополнительной нагрузки на систему кредитного скоринга, в том числе не выполняют массовых предрасчётов | АЗТ. Скоринг перегружен в рабочие часы и критичен для работы банка |
| P8 | Архитектура рассчитана на пиковый рост числа заявок и обращений после запуска маркетинговой кампании | Добавлено. Кампания запускается вместе с новым функционалом, нагрузка вырастет скачком, в том числе в кол-центре |
| **S** | **Поддерживаемость (Supportability)** | |
| S1 | В доработках максимально используются технологии, уже применяемые в банке: MS SQL, Oracle, .NET, Java, React.js | Прямое требование, снижает стоимость поддержки |
| S2 | Новые технологии допускаются, если совместимы с существующими платформами разработки и экспертиза по ним уже есть внутри банка | Прямое требование. Java-специалисты есть в команде АБС, микросервисный стек знаком команде системы кол-центра |
| S3 | В качестве шины обмена сообщениями используется Kafka | АЗТ. Выбор на перспективу, при этом текущая версия платформы интернет-банка с Kafka несовместима, что влияет на архитектуру решения |
| S4 | Функциональность открытия депозита выносится в отдельные сервисы и не реализуется внутри монолита интернет-банка | АЗТ. Позволяет не трогать ядро платформы подрядчика и получить горизонтальное масштабирование |
| S5 | Доработки ядра интернет-банка силами подрядчика исключаются, бизнес-логика реализуется командой банка | Прямое требование, обновление ядра привязано к подрядчику и удлиняет сроки |
| S6 | Готовится документация по архитектуре и интерфейсам взаимодействия для дальнейшего расширения системы | Прямое требование бизнеса, за MVP последует целевое решение |
| S7 | Интерфейсы взаимодействия версионируются и сохраняют обратную совместимость | Добавлено. Системы принадлежат разным владельцам: банк, подрядчик интернет-банка, подрядчик системы кол-центра. Несогласованное изменение контракта ломает соседнюю систему |
| S8 | Для новых сервисов собираются метрики доступности и времени отклика, настроены оповещения | Добавлено. Без измерений требование 99,9% невозможно ни подтвердить, ни оспорить |
| S9 | Журналы систем связаны сквозным идентификатором операции | Добавлено. Одна заявка проходит через пять систем, без сквозного идентификатора разбор инцидента занимает дни |
| S10 | Новые сервисы и интеграции покрыты автоматическими тестами | Добавлено. Изменения идут параллельно в нескольких системах и командах, включая внешние |
| **+R** | **Ограничения (Restrictions)** | |
| +R1 | Трафик сайта и интернет-банка защищается шифрованием | Прямое требование, передаются персональные и финансовые данные |
| +R2 | Персональные данные обрабатываются по требованиям законодательства, в журналах маскируются | Добавлено. Заявка содержит Ф. И. О., телефон и паспортные данные |
| +R3 | Новый клиент не обслуживается без личной идентификации в отделении | Ограничение банковского регулирования, задаёт офлайн-шаг в обоих сценариях |
| +R4 | Данные бэк-офиса депозитов и бэк-офиса кредитов разграничены, сотрудники не видят данные друг друга | Требование безопасности, именно оно породило текущее согласование ставок по электронной почте |
| +R5 | АБС масштабируется только вертикально | Ограничение её базы данных, снимает вариант «принимать онлайн-поток заявок в АБС» |
| +R6 | Прямая работа интернет-банка с API и базой данных АБС в новом процессе не допускается | Прямое требование. Существующая интеграция интернет-банка с БД АБС остаётся, но не расширяется |
| +R7 | Обмен между АБС и Кредитным конвейером остаётся регламентным, раз в сутки, ускорить его невозможно | Прямое ограничение из условия, определяет способ доставки онлайн-заявок в конвейер |
| +R8 | Обновление ядра интернет-банка возможно только силами подрядчика | Ограничение по платформе, влияет на сроки и на границы изменений |
| +R9 | Текущая версия платформы интернет-банка несовместима с Kafka | Ограничение, из-за которого работа с очередями выносится за пределы монолита |
| +R10 | По новому клиенту доступны только общие данные бюро кредитных историй | Ограничение полноты данных для скоринга в сценарии с сайта |
| +R11 | Полная информация об условиях кредита хранится в Кредитном конвейере | Определяет, откуда берутся условия для витрин сайта и интернет-банка |
| +R12 | Кредитный конвейер и система скоринга уже работают 24/7 и масштабируются горизонтально | Их можно использовать как есть, дорабатывать под нагрузку не требуется |
| +R13 | Система кол-центра сопровождается подрядчиком, доработки ограничены возможностями расширения платформы | Часть изменений могут выполнить Java-специалисты команды АБС |
| +R14 | Публичные формы заявок защищены от автоматизированных обращений | Добавлено. Форма на сайте доступна без авторизации, без защиты она превращается в источник мусорных заявок и лишней нагрузки на кол-центр |
| +R15 | Количество обращений в бюро кредитных историй ограничивается и контролируется | Добавлено. Запросы в бюро платные, а сценарий на сайте позволяет дёргать их анонимно и без ограничений |
| +R16 | Срок реализации MVP - 6 месяцев, целевого решения - 12 месяцев | Ограничение по срокам из целей бизнеса, определяет объём изменений в каждой системе |
